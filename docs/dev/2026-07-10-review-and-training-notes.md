## セクション1: コードレビューで発見した問題点

### バグ(重要度: 高)

1. **async_save 有効時に best_perf 更新が checkpoint に反映されない**(`mortal/train.py:927`, `mortal/train.py:836`)
   同期保存では test_play 後に `better` なら `torch.save` を再実行して更新後の best_perf を反映するが、async 経路では `state_to_cpu()` が test_play **前**に dict を deep copy するため、state_file と best_state_file の best_perf が1世代古くなる。再起動すると記録が巻き戻り、gate_sigma ゲートが既に超えた水準で再判定される。
   修正案: async 時も better なら best_perf を差し替えて再保存する。

2. **top-k 候補の追加が次の save まで永続化されない**(`mortal/train.py:947`)
   `top_checkpoints.append` が checkpoint 保存の後に走るため、次の save_every 境界前にクラッシュすると candidates/candidate_*.pth が「ディスクにあるがリストに載っていない」孤児ファイルになる。ロード時の `path.exists` フィルタ(`mortal/train.py:169`)は逆方向しか掃除しないため孤児は永久に溜まる。
   修正案: 起動時に候補ディレクトリとリストを突き合わせて掃除。

3. **weights_only=False への回帰**(`mortal/player.py:49`, `mortal/player.py:171`, `mortal/bench_inference.py:72`, `mortal/strip_checkpoint.py:25`)
   上流コミット 0cff2b5 で全 torch.load を weights_only=True に統一済みで、checkpoint はテンソルと素の dict のみなので True でロード可能(one_vs_three.py は True のまま)。特に opponent pool ディレクトリは .pth を置くだけで対戦相手になる仕組みなので、False での読み込みは pickle 任意コード実行の入口。全箇所 True に戻すべき。

4. **handle_submit_replay のパストラバーサル**(`mortal/server.py:82`)
   `path.join(S.buffer_dir, f'{S.submission_id}_{filename}')` の filename はワーカー送信の文字列そのままで、bind_host による LAN 待受け運用では `..\..\foo` 等で buffer_dir 外に書き込める。`path.basename(filename)` で塞がる。またサーバーは無認証なので LAN 上の誰でも submit_param で学習パラメータを差し替え可能な点も要認識。

5. **extract_threats のハードコードオフセット**(`mortal/train.py:336`)
   v4 obs のチャンネル 771/857 が obs_repr.rs の実装詳細に暗黙依存。エンコーダ変更時にエラーにならず黙って誤ったメトリクスを出す。Rust 側から定数をエクスポートするか検証テストを追加すべき。

### メトリクス精度の問題(重要度: 中、学習には無害)

- 条件付きメトリクス(train/threat/*, train/call/*)は `cond.any()` のときだけ加算されるのに常に metrics_batches で割る(`mortal/train.py:774`)。条件が空のバッチが多いメトリクスほど過小表示される。メトリクスごとに加算回数を数えるべき。
- `legal_action_count_max` は「バッチ内 max の平均」で名前と意味がずれている(`mortal/train.py:527`)。
- `mortal/train.py:667-671` は 572-577 で計算済みの is_call_action 等を再計算する死にコード。
- torch.quantile は約1677万要素の上限があり、all_td_abs(save_every × batch_size 要素)が設定次第で RuntimeError(`mortal/train.py:768`)。
- test_play の SE は iid 仮定だが4席複製+固定シードで相関があり厳密には不正確(目安としては可)。better ゲートは pt と rank の両方が SE マージン超えを要求するため gate_sigma を上げると best が更新不能になり得る(`mortal/train.py:862`)。

### 運用・保守(重要度: 低)

- TrainPlayer.train_play の cudnn.benchmark 復元が try/finally でない(`mortal/player.py:189`)。TestPlayer 側は finally 済みで非対称。
- start_all.ps1 の再起動ループは無条件で、設定ミス時に5秒ごとの永久クラッシュループになる。連続失敗 N 回で停止する防御を推奨。
- working tree で CLAUDE.md、docs/dev/architecture.md、docs/dev/roadmap.md が削除されたまま未コミット(コミット 30ae299 で追加されたもの)。意図的なら削除をコミット、事故なら git restore。
- Rust: `shanten_deltas_plus`(libriichi/src/algo/sp/state.rs)は tehai[tid]==4 の牌も計算し、その場合 base-5 インデックスが桁あふれして別の手牌にエイリアスするが、「壁に5枚目は存在しないので読まれない」という呼び出し側の慣習で成立。panic はしないが debug_assert かコメントを推奨。

### 問題なしを確認した点

- Rust の DeltaCalculator / prob 三角行列メモ化 / State の Hash 変更(コミット b27aa5e)は精読の結果正しい。min-plus マージの結合性の議論は妥当、30,000 手牌の等価性テスト付き、prob_cache のインデックス上界も従来と同じ制約内。
- engine.py の bucket 化・CUDA Graphs は、パディング行のマスク処理(action 45 を合法に保つ)、autocast cache_enabled=False でのキャプチャ、tolist() 同期前提の staging バッファ再利用など危険箇所を正しく処理している。live な学習モデルへの weights cast を allow_weights_cast で遮断しているのも正しい。
- checkpoint は常に save_every 境界で書かれるため、resume によるメトリクス分母ずれは起きない。

## セクション2: 牌効率の改善分析

### 前提: モデルが既に受け取っている情報

v4 obs には牌効率系特徴量が充実している(`libriichi/src/state/obs_repr.rs:395-476, 564-624`)。現在向聴数 one-hot、向聴維持打牌(keep_shanten_discards)・向聴進行打牌(next_shanten_discards)プレーン、SPCalculator による打牌候補ごとの受け入れ牌・巡目別聴牌率/和了率/EV テーブルが含まれる。問題は与える側でなく「測る手段」と「直接効く学習信号」の欠如。

### 改善提案(優先順)

1. **牌効率を直接測るメトリクスの追加(最優先)**
   現状は logged_action_argmax_rate(人間との一致率)と test_play 平均順位(3000戦で SE ±0.02)のみで、小さな改善はノイズに埋もれる。
   - (a) Rust 不要: obs の keep/next_shanten プレーンを extract_threats と同じ要領でデコードし、「無スレット・門前時に argmax 打牌が向聴進行打牌集合に入っている率(向聴後退率)」を train.py のメトリクスに追加。
   - (b) より正確: GameplayLoader に SP 最大 EV 打牌をテンソルで吐かせ、argmax 一致率と選択打牌の EV 損失を出す。SPCalculator は 2.3 倍高速化済み(b27aa5e)なので余裕がある。

2. **序中盤の学習信号が薄い**
   Q ターゲットは gamma^steps_to_done × 局報酬の MC のみ(`mortal/train.py:450`)。配牌直後の打牌は割引が最深+局結果ノイズで教師され、牌効率ミスの EV 差(数十点)は最も信号が届きにくい。AuxNet は next_rank の4次元のみ(`mortal/train.py:79`)で、opt-in 補助ヘッド追加の価値がある。候補: 打牌後の受け入れ枚数回帰、SP 最適打牌分類(DeltaCalculator でロード時に安価に生成可能)。現在向聴数の予測は obs に one-hot で入っているので無意味。

3. **向聴数4以上では SP 特徴量が空白**
   SHANTEN_THRES=3(`libriichi/src/algo/sp/calc.rs:13`)までしか計算されず、4向聴以遠はプレーンがゼロ(`libriichi/src/state/obs_repr.rs:650` 付近)。配牌〜序盤数巡は入力特徴が最貧+信号最薄の二重弱点。ただし obs チャンネル変更は全 checkpoint・baseline・プール非互換(実質 version 5)なのでコスト大。まず 1 で序盤の向聴後退を測ってから判断すべき。

4. **オフライン(CQL/AWBC)は人間の打牌に錨**
   CQL 項はログの行動から離れること自体にペナルティを課すため、データの打ち手が系統的に外す局面ではモデルも引っ張られる。AWBC の重みは局リターン由来で1打の質は見ない。min_q_weight を下げる実験は SP 一致率メトリクスとセットで行うべき。牌効率の上限を人間以上にするのは本質的にオンラインフェーズの役割。

5. **細かい点**
   player_names_files の絞り込みで BC の錨の質を上げられる(train/awbc/ess で監視)。牌効率評価は「無スレット・門前・リーチ非宣言」局面に限定して集計(extract_threats を流用可能)。

### 注意

SP テーブル自体が手変わり・打点・他家を無視した単騎モデルなので SP 一致率 100% は過剰適合。目標は「無スレット局面での SP 最適からの乖離が説明可能(打点・安全・形の柔軟性)であること」。

## セクション3: 河の特徴量と場況読み

### 河は既に深くエンコード済み(`libriichi/src/state/obs_repr.rs:209-280, 736-773`)

- 自分の河: 最初6打+直近18打のスロット(牌・赤・ドラ・カン文脈 4ch/打)+時間減衰サマリー(exp(-0.2×経過打数))。
- 他家3人の河: 最初6打+直近18打、各8ch/打(打牌・赤・ドラ・**手出し/ツモ切り**・**リーチ宣言牌**・チーポン構成牌・カン)+減衰サマリー3面(全打牌/手出し/リーチ牌)。サマリーは max_kawa_len 基準の共通時計で、河をまたいだ時系列も粗く表現される。
- 「見えている牌の枚数/4」プレーン(`libriichi/src/state/obs_repr.rs:333`)。

### 有効活用の分析

- 守備方面は既に活用されている: 放銃(約-8000点級・頻出)の濃い勾配+鳳凰卓人間の BC 転写。
- 深い読み(手出しパターンからの待ち推定)は正解ラベルが与えられないのがボトルネック。入力を足しても信号が薄ければ使われない。
- 推奨は入力追加ではなく**後知恵(hindsight)ラベルの補助タスク**: 牌譜には全員の手牌が写っており、`libriichi/src/dataset/invisible.rs:152-245` が各他家の正確な手牌・向聴数・待ち牌・フリテン・山の実際の並びを既にパース済み。

### 場況読み→牌効率への組み込み(3経路と3案)

**3経路**

| 経路 | 内容 | 状態 |
|---|---|---|
| (a) | 枚数カウント | 実装済み |
| (b) | 山読み(見えない牌の山/他家の手の区別) | 空白。SPCalculator は見えない牌がすべて等確率で山にあると仮定 |
| (c) | 出アガリ期待 | SP はツモ専モデルで見ていない |

**3案**

- 案A: SPCalculator に確率的な壁を導入 → 非推奨(整数組合せ論が崩れ、ビット同一テスト資産も失う)。
- 案B: 手工の山読み特徴量を obs に追加 → 非推奨(全 checkpoint 非互換+手作りヒューリスティックは NN に学ばせるより弱い)。
- **案C(推奨): 後知恵ラベルの補助タスク**。「牌種ごとの山の実残数(34次元 0-4)」「各他家の聴牌有無・待ち牌」を AuxNet に予測させる。トランク φ が河→山/手の推定(=場況読み)を強制学習し、Q ヘッドが待ち選択に織り込める。obs 不変で互換性を壊さず、AWBC 同様の opt-in にできる。

### 検証メトリクス

SP 上ほぼ同受け入れの候補が複数ある決定点で「実際の山に多く残っていた方」を選べた率(山は後知恵で分かるため offline で計算可能)。

### 期待値

正直小さい(僅差の待ち選択・リーチ判断のタイブレーク)が、「完璧にする」目標の最終段として正しい位置づけ。

## セクション4: 学習戦略(最重要の結論)

### 基本認識

この問題は理論の正しさでは勝てない。「人間データの BC 錨 × MC リターンの高分散 × 2フェーズの分布シフト × 順位という遅い評価」が絡む非線形システムで、介入の合成結果は予測不能。最適戦略は**フィードバックループを短くし、失敗を安く可視化し、壊れたら戻れるようにして1変数ずつ動かす**こと。

### 具体策

1. **決定点ベンチマークスイート(全ての土台)**
   ホールドアウト牌譜から決定点を数万〜十万点固定サンプリングし、SP 最適打牌/後知恵の山残数/スレット文脈/人間の打牌をラベル付けした凍結スイートを作る。checkpoint ごとにフォワード1回・数分で採点でき、同一局面比較なのでノイズほぼゼロ。守備崩壊(無スレット局面の none 率上昇など)がステップ単位の曲線で見える。

2. **線形プローブによる安い反証**
   補助タスク投入前に、凍結トランクの φ に線形ヘッドだけ乗せてラベル予測(1時間)。精度が既に高ければ情報は φ にあり補助タスク不要 → 数週間の再学習を回避できる。低ければ勝ち筋あり。プローブ精度自体が場況読み獲得度メトリクスになる。

3. **オンライン守備化のメカニズムと対策**
   - (a) オンラインは CQL が切れて錨がない(`mortal/train.py:461`)。対策: リプレイ混合(人間牌譜を1〜2割、dataloader のファイルリスト混合で実装可)または凍結オフラインポリシーへの KL 正則化。
   - (b) 強い baseline 3人相手だと押しの成功体験が構造的に不足する。対策: 既存のプール対戦相手機能で弱め・多様な相手を混ぜ、押しに正の credit が流れる経路を確保(opponent_pool_prob がダイヤル)。
   - (c) Huber 損失は守備化バイアスを持ち得る。局報酬分布は「頻繁な小さい負+稀な大きい正(和了)」に歪んでおり、Huber が切る外れ値は主に和了報酬 → 押しの価値が系統的に過小評価される。オンライン持ち込みは要再検討。
   - (d) 探索がほぼゼロ(ε=0.005, temp=0.05)。対策: 一部ワーカーだけ探索強めのプロファイルで回す。
   - (e) 補助タスクはオンラインでも回し続ける(自己対戦ログは全情報を持つ)。干渉監視は実装済みの grad/aux_norm / grad/dqn_norm を使う。

4. **実験プロトコル**
   1介入=1実験。成功/中止基準を事前に書く(例: SP一致率+1pt 以上かつ houjuu_rate が基準帯内かつ test_play ペア比較悪化が gate_sigma 以内、20k ステップで未達なら revert)。比較は常にペア(固定シード 10000+/key 0x2000 は checkpoint 間ペア比較として正しい設計)。top-k candidates と gate_sigma でロールバックする。

5. **推奨順序**
   (1) スイート+スタイルダッシュボード(和了/放銃/立直/副露率の許容帯アラート) → (2) 線形プローブ → (3) プローブが正当化した場合のみオフラインで aux 導入(凍結トランクでヘッドをウォームスタート→小さい重みで解凍) → (4) オンライン移行はリプレイ混合+プール多様化+探索プロファイルを最初から入れ、崩れたら top-k から巻き戻す。

6. **期待値管理**
   個々の介入の多くは効かない前提で臨む。計画の価値は当たりの保証ではなく、外れを数日と曲線1本で確定させ、当たりだけが積み上がる構造にすること。観測と可逆性への投資が理論の精緻化より期待値が高い。
